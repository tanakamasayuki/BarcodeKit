# 要件

内部の設計記録。日本語のみ。利用者向けの情報は [../README.ja.md](../README.ja.md) と [FORMATS.ja.md](FORMATS.ja.md) にある。

この文書は最初のたたき台（`memo.ja.md`）を書き直したもの。たたき台自体はリリース前に削除したが、git 履歴には残っている。たたき台から変えた点とその理由は [DECISIONS.ja.md](DECISIONS.ja.md) §3 にある。

## 1. 何を作るか

BarcodeKit は、組み込み環境向けに 1次元バーコードと 2次元コードを**生成する**ライブラリである。

入力データを、バーコード規格に従った**論理的な白黒モジュールのパターン**へ変換することが唯一の責務であり、液晶・電子ペーパー・プリンタへの出力方法は利用者が決める。

## 2. 目的

- 複数のバーコード形式を共通の考え方で扱えるようにする
- 表示デバイスや描画ライブラリに依存しない構成にする
- Arduino など限られたメモリ環境でも使えるようにする
- 符号化・チェックディジット・誤り訂正といった規格上の処理をライブラリ側で完結させる
- 生成した白黒パターンを、利用者が自由な方法で描画・印刷・転送できるようにする
- 必要な形式だけを選んで使えるようにする
- 将来の形式追加を妨げない設計にする

## 3. 対象環境

| 環境 | 位置づけ |
| --- | --- |
| ESP32 系 | 主対象。CI で常時ビルド検査する |
| AVR 系（Uno など） | 主対象。1次元形式が動くことを CI で保証する。QR は大きいバージョンを扱えない |
| RP2040 系 | 動くはずだが**未検証**。CI のジョブはあるが、対象となる example のプロファイルがまだ無い |
| SAMD 系 | 同上 |
| その他 Arduino 互換 / C++ 環境 | 動くはずだが検証しない |

特定の表示デバイス、ディスプレイライブラリ、通信方式には依存しない。

C++ 標準は **C++11** を下限とする（Arduino AVR コアの既定に合わせる）。

## 4. 対象利用者

- Arduino でバーコードを表示したい開発者
- OLED や TFT 液晶に QR コードを出したい開発者
- 電子ペーパーに JAN コードや Code 128 を出したい開発者
- 小型プリンタへバーコードパターンを送りたい開発者
- 複数形式を1つのライブラリで扱いたい開発者
- 表示処理と生成処理を分離したい開発者

バーコード規格に詳しくない開発者が主な読者である。エラーメッセージ・設定名・ドキュメントはその前提で書く。

## 5. 責務の範囲

**ライブラリの責務に含む**

- 入力データの受付
- 入力値の妥当性確認
- 形式ごとの符号化
- チェックディジットの計算・検証・付加
- 誤り訂正情報の生成（QR）
- 白黒モジュールの生成
- 出力サイズ情報の提供
- 推奨クワイエットゾーン情報の提供
- エラー内容の通知

**中核の責務には含まない（同梱ヘルパーまたはサンプルで扱う）**

- 特定ディスプレイへの描画 → `BarcodeKitDraw.h`（任意インクルード）と examples
- 特定プリンタへの印刷 → 将来のサンプル

**対象外**

- カメラ画像からの読み取り・デコード
- 画像補正・画像認識
- 画像ファイル（PNG/BMP）の生成
- 通信機器固有の出力制御
- GUI の提供
- HRI（バーコード下の数字表記）の描画 — 文字列は `text()` で提供するが描画はしない
- GS1 アプリケーション識別子の解釈・検証
- ラベルレイアウト・帳票生成
- 回転描画・非整数倍率
- 印刷品質・読み取り成功率の保証
- バーコード規格の認証取得

## 6. 基本方針

### 6.1 生成専用

読み取り・デコードは対象外とする。デコードには画像取得・二値化・傾き補正・領域検出・パターン解析が必要で、生成に比べ計算量とメモリが桁違いに大きい。専用スキャナや画像認識ライブラリを使うほうが適している。

### 6.2 描画処理との分離

符号化処理と描画処理を明確に分ける。ライブラリは「各位置が黒か白か」を提供し、利用者が任意の描画ライブラリや出力装置へ渡す。

### 6.3 デバイス非依存

`BarcodeKit.h` は Adafruit GFX / TFT_eSPI / U8g2 / LovyanGFX / 電子ペーパー / サーマルプリンタのいずれにも依存しない。連携は `BarcodeKitDraw.h`（任意）と examples で示す。

### 6.4 軽量性

メモリ使用量とプログラムサイズを抑える。動的確保は行わず、必要メモリはコンパイル時に確定する。使わない形式のコードと符号表はリンカで落ちる。

### 6.5 統一性

形式ごとに違う使い方を強いない。`encode()` / `width()` / `height()` / `module()` という共通の作法を全形式で揃える。ただし形式固有の設定（QR の誤り訂正レベルなど）はその形式のクラスにだけ置く。

## 7. 機能要件

| # | 要件 | 対応する設計 |
| --- | --- | --- |
| F1 | 生成する形式を明示的に指定できる | 形式ごとのクラス（[CORE_DESIGN.ja.md](CORE_DESIGN.ja.md) §2） |
| F2 | 文字列またはバイト列で入力を指定できる | `encode()` の2種のオーバーロード |
| F3 | 形式ごとの規則で入力を検証する | [FORMATS.ja.md](FORMATS.ja.md) の文字種・桁数表 |
| F4 | 使用不可文字・桁数不足・桁数超過・容量超過・設定不正・チェックディジット不一致を検出する | `Error` 列挙（CORE_DESIGN §3） |
| F5 | チェックディジットを自動計算・検証・付加できる | 形式ごとの規約（FORMATS） |
| F6 | QR で誤り訂正レベル・バージョン自動選択・バージョン指定・容量判定を扱える | CORE_DESIGN §6.7 |
| F7 | 白黒モジュールの状態を取得できる | `module(x, y)` |
| F8 | 幅・高さ・種類・推奨余白・設定・最終データを取得できる | 共通 API（CORE_DESIGN §2.1） |
| F9 | 推奨クワイエットゾーンを提供する | `quietLeft/Right/Top/Bottom()` |
| F10 | 小容量 RAM 環境で使える | 呼び出し側バッファ方式（CORE_DESIGN §4） |
| F11 | エラー原因を判別できる情報を返す | `Result`（`Error` + 入力位置） |

## 8. 非機能要件

| 項目 | 目標 | 検証方法 | 現状 |
| --- | --- | --- | --- |
| 移植性 | AVR / ESP32 でコンパイルできる。RP2040 / SAMD も動くはず | CI の arduino-cli ビルド検査 | AVR・ESP32 は検査済み。**RP2040 / SAMD は未検査**（example にプロファイルが無い） |
| 外部依存 | 本体はゼロ。標準ヘッダも `<stdint.h>` `<stddef.h>` `<string.h>` のみ | ホストビルドで確認 | 確認済み |
| メモリ効率 | 動的確保ゼロ。必要量をコンパイル時に知れる | `malloc` フックを仕掛けたホストテスト（`noalloc/`） | 確認済み。11 形式すべてと結果の読み出しで確保 0 |
| 安定性 | 不正入力で範囲外アクセス・メモリ破壊・停止が起きない | ファジングテスト（`fuzz/`、ASan/UBSan 有効） | 確認済み。2 シード × 20,000 回。**Code 93 の表外読み出しをこれで発見した** |
| 再現性 | 同じ入力・設定から常に同じパターン | 既知ベクタテスト、`determinism/` テスト | 確認済み |
| 可読性 | 名称・設定・エラーがバーコードに不慣れでも分かる | ドキュメントレビュー | [GUIDE.ja.md](GUIDE.ja.md) / [API.ja.md](API.ja.md) を整備 |
| 拡張性 | 形式追加で既存形式の使い方を変えない | 形式追加時に全テスト再実行 | 11 形式を足す間、共通 API は変えずに済んだ |

残る未検証は RP2040 / SAMD のビルドと、実機のスキャナでの読み取り確認（[MANUAL_TEST.ja.md](MANUAL_TEST.ja.md)）。

## 9. 想定ユースケース

| # | 場面 | 使う形式 |
| --- | --- | --- |
| U1 | 電子ペーパー・液晶に JAN コードを出し、外部スキャナで読む | EAN-13 / EAN-8 |
| U2 | 設定 URL や識別情報を QR で表示する | QR Code |
| U3 | 機器番号・シリアル番号を表示する | Code 128 / Code 39 |
| U4 | 整理番号・受付情報を小型プリンタへ出力する | Code 128 / ITF |
| U5 | Wi-Fi 接続情報を QR で表示する | QR Code |
| U6 | 箱番号・ロット番号・管理番号を表示または印刷する | ITF / ITF-14 / Code 128 |

U1 と U6 が「ガードバーの延長」「ベアラバー」といった描画上の要求を持ち込むため、描画ヘルパーの要件に反映している（CORE_DESIGN §7）。

## 10. 品質目標

- 規格に従った正しいバーコードを生成できる
- 一般的なスキャナで読み取れるパターンを生成できる
- 不正入力を適切に拒否する
- 小容量マイコンでも使い方を選べる
- 表示デバイスに依存せず再利用できる
- 複数形式を一貫した考え方で扱える
- 新しい形式を継続的に追加できる

読み取り可否は表示サイズ・解像度・コントラスト・余白・印刷品質・スキャナ性能にも左右されるため、**すべての環境での読み取り成功は保証しない**。この点は README にも明記する。
