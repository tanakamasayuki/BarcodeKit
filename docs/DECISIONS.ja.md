# 設計決定

内部の記録。日本語のみ。「なぜそうなっているか」の台帳。

決定の内容そのものは [CORE_DESIGN.ja.md](CORE_DESIGN.ja.md) にある。ここには**理由と、採らなかった選択肢**を書く。

## 1. 確定した決定

### D1. メモリは呼び出し側が提供する

`encode(input, buf, bufSize)` の形で利用者がバッファを渡し、ライブラリは `new` / `malloc` を一切使わない。必要サイズは `bufferSize()` が `constexpr` で返す。

**理由**: 対象環境に AVR（RAM 2 KB）が含まれる。動的確保は断片化と失敗経路を持ち込み、失敗時の扱いを全形式に波及させる。呼び出し側バッファなら失敗は「バッファが足りない」の 1 種類にまとまり、しかもコンパイル時に検出できることが多い。

**採らなかった案**:
- *テンプレートで内部固定配列*（`QRCode<10>`）— 宣言は簡潔だが、実行時に上限を変えられず、同じ形式の別サイズが別の型になるため描画ヘルパーやコンテナの扱いが煩雑になる。
- *内部で malloc* — 実装は最も簡単だが上記の理由で不採用。
- *1次元はバッファ不要（都度計算）+ QR だけバッファ* — RAM は最小になるが、形式によって使い方が変わり [REQUIREMENTS.ja.md](REQUIREMENTS.ja.md) の統一性要件に反する。逐次生成は将来拡張として残す。

### D2. 形式ごとに独立したクラス

`BarcodeKit::Code128` / `EAN13` / `QRCode` …。仮想関数も抽象基底も使わない。

**理由**: 使った形式だけがリンクされる（未使用の符号表が Flash を食わない）。形式固有の設定を型安全に表現できる。共通性は「同じ名前のメンバを揃える」ことで足り、汎用処理はテンプレートで受けられる。

**採らなかった案**: *単一クラス + `Format` enum で実行時切替* — 設定で形式を変えられる利点はあるが、全形式のコードがリンクされて Flash を食う。将来必要になれば enum ディスパッチのラッパを別ヘッダで足せる（後方互換のまま追加できる）。

### D3. QR は nayuki QR-Code-generator を移植する

MIT ライセンス。API とメモリ方式は BarcodeKit 側に合わせ、ライセンス表記を残す。

**理由**: リードソロモン誤り訂正・マスク評価・カーソル配置は実装量が大きく、バグを入れても「読めない QR」としてしか現れず原因究明が難しい。実績のある実装を土台にしたほうが初期リリースの品質と速度が両立する。

**採らなかった案**: *フルスクラッチ* — 外部由来コードがゼロになるが、初期リリースが大きく遅れる。*QR を次バージョンに回す* — memo の初期目標「1次元と QR を共通ライブラリで扱える」から外れる。

### D4. クワイエットゾーンは出力パターンに含めない

`width()` / `module()` は常にシンボル本体のみ。推奨余白は `quietLeft/Right/Top/Bottom()` で別途取得する。描画ヘルパーは既定で余白を付ける。

**理由**: 3 つある。
- 背景色を自分で塗る利用者やプリンタへ送る利用者が、余白を剥がせなくなるのを避ける
- EAN-13（左 11 / 右 7）のように非対称な余白があり、「含める」と `width()` の意味が形式ごとにぶれる
- オプション切替にすると `width()` の意味が設定依存になり、ドキュメントとテストが倍になる

**採らなかった案**: *常に含める*（初心者には安全だが上記の不都合）、*オプションで切替*（`width()` の意味が揺れる）。

### D5. 描画ヘルパーは同梱の別ヘッダ

`BarcodeKitDraw.h`。中核は描画ライブラリ非依存の汎用コールバック版で、その上に LovyanGFX / M5GFX 系アダプタと Serial（ASCII）アダプタを載せる。`BarcodeKit.h` の外部依存はゼロのまま。

**理由**: 「倍率計算・センタリング・余白・ガードバー延長」は利用者が必ず自作することになり、しかも間違えると読めないバーコードになる。ライブラリ本体の依存を増やさずにこれを吸収できる。

**採らなかった案**: *汎用コールバックのみ*（LovyanGFX 利用者が毎回ラムダを書く）、*Adafruit GFX / U8g2 まで対応*（テストとメンテの対象が増え初期リリースが重くなる。将来拡張）。

### D6. 初期リリースは 11 形式

Code 39 / Code 93 / Code 128 / EAN-8 / EAN-13 / UPC-A / UPC-E / ITF / ITF-14 / Codabar / QR Code。

**理由**: EAN/UPC の 4 形式は符号表を共有する同一ファミリ、ITF-14 は ITF に桁固定とチェックディジットを足すだけ、Code 93 も Code 39 の隣。memo の初期候補 8 形式に対する追加コストが小さいのに対し、「1次元の主要形式が一通り揃っている」ことの価値は大きい。

### D7. 自動テストはホスト実行のみ

実機は examples を使った手動確認に分ける。CI での実機ビルドは「コンパイルが通ること」だけを見る。

**理由**: 実機テストは CI に接続実機を要求し、失敗の切り分けが難しい。バーコード生成は純粋な計算なのでホストで完全に検証でき、実機で新たに分かることは「実際のスキャナで読めるか」だけ。それは手動確認のほうが適している。

### D8. 利用者向け examples は M5Unified ベース

テスト用スケッチ（ホスト）とは分ける。

**理由**: 実機確認は M5Stack Core BASIC で行う。M5Unified なら M5 系の機種差を吸収でき、利用者にもそのまま渡せる。テスト用スケッチは描画を伴わないものが大半なので、共有する利点が薄い。

### D9. `text()` の上限超過では `nullptr` を返す

内部固定バッファ（既定 48 文字、`BARCODEKIT_TEXT_MAX`）に収まらない入力では `text()` が `nullptr` を返す。`encode()` 自体は成功する。

**理由**: 入力文字列へのポインタを返す設計にすると、利用者の入力バッファの寿命に依存する罠になる。チェックディジットを付ける形式は最大 14 桁程度なので、既定 48 で実用上は足りる。

### D10. narrow:wide 比の既定は 3:1

Code 39 / ITF / Codabar。`setRatio(2)` で 2:1 も選べる。

**理由**: 規格上は 2.0〜3.0 が許容範囲。低解像度の液晶や電子ペーパーでは 3:1 のほうが太細の差が明確で読み取りやすい。幅を詰めたい場合に 2:1 を選べるようにする。

### D11. コンパイル時スイッチは 2 つだけ

`BARCODEKIT_TEXT_MAX` と `BARCODEKIT_NO_ERROR_MESSAGES`。形式ごとの有効／無効マクロは用意しない。

**理由**: ヘッダオンリーでリンカが未使用シンボルを落とすため、形式ごとのマクロは効果が薄い。厳密に制御したい利用者は `#include <BarcodeKit/Code128.h>` と個別に書ける。スイッチが増えるとテストする組み合わせが増える。

### D12. リリース自動化は arduino-library-release-toolkit をコピー

`tools/bump_version.py` と `.github/workflows/release.yml`。

**理由**: 兄弟プロジェクトと同じ運用にする。toolkit 側が更新されたときは、toolkit の `sync_release_assets.py` が各リポジトリへ配る（配る側のスクリプトなので、このリポジトリには置かない）。

### D13. ドキュメントは docs/ 配下にテーマ別

ルートには README / CHANGELOG / LICENSE / keywords.txt / library.properties だけを置く。

**理由**: 最近の兄弟プロジェクト（EspBle / ESP32KeyBridge / EspMidi）がこの形。1 枚の SPEC だと「利用者が何度も引く形式表」と「開発者しか読まないテスト計画」が同居する。言語方針も 3 段に分ける（[README.ja.md](README.ja.md) 参照）。

## 2. 明示的に持たない機能

| 機能 | 理由 |
| --- | --- |
| デコード・読み取り | 生成に比べ計算量とメモリが桁違い。専用スキャナや画像認識ライブラリのほうが適している |
| HRI（バーコード下の数字）の描画 | フォント依存が強く、配置の好みも分かれる。`text()` を提供して利用者に委ねる。将来拡張 |
| 画像ファイル生成 | 出力先は利用者が選ぶ、という基本方針に反する |
| 回転・非整数倍率 | 非整数倍率はモジュール幅が不均一になり読み取り性能を落とす。回転は描画ライブラリ側の機能 |
| GS1 の業務ルール | バーコード生成の範囲を超える。GS1-128 の符号化自体は将来拡張 |
| 読み取り成功率の保証 | 表示サイズ・解像度・コントラスト・余白・スキャナ性能に依存し、ライブラリ単独では保証できない |

## 3. 最初のたたき台から変えた点

このライブラリは `memo.ja.md` という要件のたたき台から始まった。たたき台自体はリリース前に削除したが（git 履歴には残っている）、**そこから変えた判断は残す価値があるのでここに写しておく**。左列はたたき台に書かれていた内容。

| たたき台での記述 | 本仕様での扱い | 理由 |
| --- | --- | --- |
| Code 93 / UPC-E / ITF-14 は「将来の追加候補」 | 初期リリース対象へ格上げ | D6 |
| クワイエットゾーンを出力に含めるかは「一貫した方針を定めること」（未決） | 「含めず、情報として提供」に確定 | D4 |
| 逐次的に出力を処理できる利用形態を検討する | 初期リリースでは採用せず将来拡張へ | D1。呼び出し側バッファ方式で必要メモリが小さく予測可能になり、逐次化の動機が薄れたため |
| エラー区分に「未対応形式」を含める | 持たない | 形式がクラスなのでコンパイル時に解決する |
| エラー区分に「メモリ不足」を含める | `BufferTooSmall` に統合 | 動的確保をしないため |
| 描画は「サンプルとして提供」 | サンプルに加え `BarcodeKitDraw.h` を同梱 | D5 |
| 品質目標に「一般的なスキャナで読み取れる」 | 手動確認の項目として手順化（[MANUAL_TEST.ja.md](MANUAL_TEST.ja.md)） | D7。自動テストでは確かめられないため |
| 「バーの種類や高さが異なる形式にも対応可能な情報を提供する」 | `barExtends(x)` として具体化 | EAN/UPC のガードバーがデータバーより下へ伸びることを表現するため |
| 「推奨クワイエットゾーンに関する情報の提供」 | 四方別のアクセサにした | EAN-13 の左 11 / 右 7 のような非対称な余白があるため |
